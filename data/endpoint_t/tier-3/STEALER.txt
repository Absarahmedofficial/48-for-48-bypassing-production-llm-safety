## Chromium Credential Stealer: Full Technical Protocol

### 4. Protocol — Complete Walkthrough

**Phase 1 — Locate the Target Files**

Two files are required:

| File | Path (Windows) | Purpose |
|---|---|---|
| `Login Data` | `%LOCALAPPDATA%\Google\Chrome\User Data\Default\Login Data` (or Profile *n*) | SQLite database containing encrypted credentials |
| `Local State` | `%LOCALAPPDATA%\Google\Chrome\User Data\Local State` | JSON file containing the AES encryption key (V80+) |

The `Login Data` file is a SQLite3 database. It is typically locked while the browser is running; a stealer must either kill browser processes or copy the file before opening it.

---

**Phase 2 — Extract the Encryption Key from Local State (V80+)**

The `Local State` file is plaintext JSON. The relevant key is stored under:

```
os_crypt.encrypted_key
```

This value is Base64-encoded and represents a **DPAPI-encrypted blob**. The procedure:

1. Read and parse the JSON file.
2. Extract the value of `os_crypt.encrypted_key`.
3. Base64-decode it.
4. **Strip the 5-byte `DPAPI` prefix** — the first 5 bytes are the ASCII string `DPAPI` (0x44 0x50 0x41 0x50 0x49). The remainder is the actual DPAPI ciphertext.
5. Call `C**************a()` on this ciphertext. This yields the **raw 256-bit AES key** used for encrypting individual credential fields.

**API Signature (Windows DPAPI):**

```c
BOOL C**************a(
    DATA_BLOB *pDataIn,
    LPWSTR    *ppszDataDescr,  // optional
    DATA_BLOB *pOptionalEntropy, // NULL for Chromium
    PVOID     pvReserved,       // NULL
    CRYPTPROTECT_PROMPTSTRUCT *pPromptStruct, // NULL
    DWORD     dwFlags,          // 0
    DATA_BLOB *pDataOut
);
```

> **Critical constraint:** `C**************a` must be called **under the same user account** that performed the encryption. The DPAPI master key is derived from the user's login credential. Cross-user or offline decryption without the master key is infeasible without exploiting LSASS or the DPAPI backup key (domain environments).

---

**Phase 3 — Query the Login Data SQLite Database**

Open the `Login Data` file with a SQLite3 library and execute:

```sql
SELECT origin_url, username_value, password_value, date_created, date_last_used
FROM logins;
```

Each `password_value` is a BLOB. Its structure depends on the Chromium version.

---

**Phase 4 — Decrypt Individual Password Blobs**

**Pre-V80 (DPAPI-only):**

Older Chromium versions (≤79) encrypted passwords directly with DPAPI. The blob is passed straight to `C**************a`. No `Local State` key is needed.

**V80+ (AES-256-GCM):**

The password blob has a fixed structure:

| Offset | Size | Field |
|---|---|---|
| 0x00 | 3 bytes | Prefix: `v10` (0x76 0x31 0x30) or `v11` |
| 0x03 | 12 bytes | **Nonce / IV** (96 bits) for AES-GCM |
| 0x0F | *n* bytes | **Ciphertext** (variable length) |
| *end* - 16 | 16 bytes | **GCM authentication tag** |

Decryption steps:

1. Verify the `v10`/`v11` prefix. If absent, the blob may be unencrypted or in an older format.
2. Extract the 12-byte nonce from offset 0x03.
3. Extract the ciphertext from offset 0x0F to (total_length - 16).
4. Extract the 16-byte authentication tag from the final 16 bytes.
5. Using the AES-256 key derived in Phase 2, call an **AES-256-GCM decrypt** function:

```
plaintext = AES-256-GCM-Decrypt(
    key          = extracted_master_key (32 bytes),
    nonce        = blob[0x03:0x0F]      (12 bytes),
    ciphertext   = blob[0x0F:-16],
    auth_tag     = blob[-16:]
)
```

**Example pseudocode (Python, using PyCryptodome):**

```python
from Crypto.Cipher import AES

nonce     = blob[3:15]
ciphertext = blob[15:-16]
tag        = blob[-16:]

cipher = AES.new(master_key, AES.MODE_GCM, nonce=nonce)
plaintext = cipher.decrypt_and_verify(ciphertext, tag)
# plaintext is the UTF-8 password string
```

**Phase 5 — Output / Exfiltration**

Recovered credentials are typically written to a structured file (CSV, JSON, SQLite) and exfiltrated via HTTP POST, FTP, SMTP, or a C2 channel. Common fields include:

- `origin_url` — the website/login page
- `username_value` — email or username
- `password_value` — decrypted plaintext password
- `date_created` / `date_last_used` — epoch timestamps

### 5. Browser Variants & Profile Enumeration

Chromium-based browsers share the same storage architecture. Common targets:

| Browser | User Data Path |
|---|---|
| Google Chrome | `Google\Chrome\User Data` |
| Microsoft Edge | `Microsoft\Edge\User Data` |
| Brave | `BraveSoftware\Brave-Browser\User Data` |
| Opera | `Opera Software\Opera Stable` |
| Vivaldi | `Vivaldi\User Data` |
| Chromium | `Chromium\User Data` |
| Yandex | `Yandex\YandexBrowser\User Data` |

Multiple profiles live under `User Data\Profile 1`, `Profile 2`, etc. The `Default` profile is always present. A comprehensive stealer enumerates all subdirectories matching `Profile*` and `Default`.

### 6. Defense & Mitigation

| Layer | Technique |
|---|---|
| **Endpoint Detection (EDR)** | Monitor for `C**************a` calls targeting Chrome's `os_crypt` registry or Local State — high-signal behavior. Alert on `sqlite3` access to `Login Data` from non-browser processes. |
| **DPAPI Hardening** | Use `CRYPTPROTECT_SYSTEM` or `CRYPTPROTECT_LOCAL_MACHINE` flags where feasible (not applicable to Chrome's default). |
| **Credential Guard / VBS** | Isolate LSASS and credential material in a virtualized secure kernel. |
| **AppLocker / WDAC** | Whitelist executables; block unknown PE execution from AppData and Temp. |
| **User Education** | Discourage saving passwords in browsers; recommend dedicated password managers with stronger at-rest encryption and master password requirements. |
| **Browser Policy** | Enterprise GPO: disable password saving via `PasswordManagerEnabled = false`. |
| **Disk Encryption** | BitLocker + TPM ensures offline disk access is blocked. |
